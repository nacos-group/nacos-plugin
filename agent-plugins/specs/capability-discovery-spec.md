# 按任务意图发现能力

本文细化 F02 和[功能规范](functional-spec.md)的自动化边界：用户提出业务目标时，
Agent 可在已配置的 Nacos 中寻找有助于完成任务的能力，不要求用户预先知道资源名、类型或插件名。
搜索与版本契约继续遵循[资源管理](resource-management-spec.md)，接入遵循
[装配与更新](assembly-sync-spec.md)和[Agent 互联](agent-interoperability-spec.md)。
本文是跨应用行为与实现方案；具体入口、工具名、应用加载方式及实测状态归各应用适配。

## 1. 触发与不触发

| 情况 | 行为 |
| --- | --- |
| 需要根据线索进行专业识别/检索、查询业务系统数据或使用团队规则，当前没有已知合适的能力或可靠的已提供信息 | 在规划任务时进入发现流程，不要求先尝试失败，也不要求预知中心一定存在候选。 |
| 需要专用领域流程、系统集成或自动化，当前没有适用工作流，准备自行编写实现 | 在编写该专用方案前发现一次可复用能力；普通代码修改或任务篇幅长不单独构成触发。 |
| 用户需要外部工具、数据源或专业工作流，当前可用能力不能完成 | 可隐式进入发现流程，无需提到 Nacos。 |
| 初次检索或工具调用成功返回，但没有可用结果，中心可能提供专业检索能力 | 在重复同类搜索、放弃或要求用户补足未找到的证据前，进行一次有界能力发现。工具可用不代表已满足任务。 |
| 用户询问是否有现成方案或可复用能力 | 搜索当前已配置资源中心；用户明确指定来源时遵循其选择。 |
| 已有适用工具、已加载 Skill、已连接服务或可靠的已提供信息足够完成任务 | 直接使用；不因存在“查找”等词或单纯不认识某个名词而额外搜索。 |
| 用户指定确切资源或要求安装/更新/发布 | 进入相应资源流程，不强制经过泛化搜索。 |
| 用户要求仅本地处理、禁止联网或排除资源中心 | 不触发远端搜索。 |
| 缺少执行任务所必需的用户输入，或已有调用被认证、权限、策略拒绝 | 分别澄清输入、处理访问问题；不将其当作无结果回退，不通过其他资源绕过限制。 |
| 应用未加载插件工具，或连接尚未配置 | 如实说明缺少入口/配置，继续可独立完成的工作；需要时交接初始化，不自动安装插件或改写配置。 |

“没有匹配 Skill”不等于“缺少能力”：模型自身、代码工具或已有数据可能足以完成任务。
同样，“存在网页搜索、终端或代码执行工具”也不等于“已有适用的专业能力”。判断具体需要
何种证据、数据或流程，以及现有能力是否覆盖它；不要求证明所有其他办法都失败后才发现。
发现入口不能只响应“安装插件”“找 Skill”等技术表达；“按情节识别作品”“查询物流进度”
“按团队规范检查接口”等普通目标同样可触发。对应规则应跨语言、同义表达保持一致，
不能将电影测试样例、行业名或少数关键词变成唯一触发条件。
判断限于当前会话已暴露的工具、技能和必要的能力发现机制，不为判断是否缺能力扫描整个磁盘。
用户明确的产品、数据源和执行范围不能被推荐资源替换。

### 1.1 决策时机

1. **规划时**：识别任务中需要专业检索、业务访问、团队流程或专用自动化的部分。
   有已知适用能力或足够的输入就直接使用；否则发现一次，不必先绕到通用搜索或自建实现。
2. **执行中**：初次调用没有有效结果时，在反复改词前进行发现；已做过同一需求的发现则复用结果。
3. **交接前**：准备报告能力不足，或让用户手动找工具、导出数据、代做专业流程时，
   检查该需求是否尚未尝试发现。必要用户输入的澄清和权限问题仍按原边界处理。

这三个时机共用一次发现预算，不是每到一个时机都重新搜索。混合任务只发现尚未覆盖的部分。

## 2. 可复用的实现方案

采用“发现入口 + 只读搜索工具 + 现有类型流程”的组合：

1. 用应用可加载的 Skill 或等价指令承载触发条件。名称与简短描述必须让模型识别
   专业任务的主动发现、能力缺口与无有效结果回退，详细流程在选中入口后再读取。
2. 读取本地连接摘要，固定 registry、namespace、身份和上下文指纹。读取摘要不代表
   远端当前可访问，首次搜索的成功/错误才提供本次访问证据。
3. 将需求转为最少量能力关键词，以支持的资源类型查询 Nacos Client API。
4. 依据返回的能力描述选择候选；将选定身份和用户原任务交给已有类型流程。
5. 按已有授权完成使用准备，核验应用可用性，再继续原任务。

这是模型选择与编排方案，不引入监听全部对话的后台程序，不注入应用全局指令，
也不把插件声明当作应用的确定性“能力缺失回调”。隐式发现有赖于入口被加载及应用选择策略；
未实测的应用不得宣称已支持或保证每次触发。

### 2.1 跨应用引导词与暴露位置

各应用可用下列语义作为发现入口的短描述基线；实际工具名、资源类型和支持范围由适配填入，
不得照抄未实现的能力。英文用于插件元数据，中文规则见第 1 节，两者表达同一决策标准：

> Discover reusable capabilities in Nacos for specialized lookup or identification, business data,
> team rules, and domain workflows or automation not covered by a known suitable skill or service.
> Use when users ask for an existing solution, before building a custom solution for these needs or reporting a capability gap, and after
> an initial search or tool attempt yields no useful result. Ordinary requests need not mention
> Nacos, plugins, Skills, MCP, or Agents. Skip direct answers from supplied information and tasks
> already covered by a suitable capability; respect source restrictions.

暴露层分别承担以下职责：

| 层 | 应提供的信息 |
| --- | --- |
| Skill 名称/描述或应用等价的选择元数据 | 说明帮助完成哪些任务、何时发现；触发条件放在正文加载之前可见的位置。 |
| 搜索工具描述及支持时的 MCP 服务器说明 | 同样呈现主动发现和失败回退语义，保留上下文、预算、只读发现与执行边界；不能只写“搜索注册中心”。 |
| 工作流正文 | 连接摘要、最小查询、预算、候选甄别与按类型交接，并给出少量跨领域正反例。 |
| 应用实际接入 | 将入口和工具暴露给新会话，区分“目录可见”“正文已读”“工具可调用”；静态声明不能替代运行验证。 |

使用简短动作与条件，避免只有“能力缺口”等抽象术语、靠技术词触发或在描述中堆砌行业词。
不要求模型输出内部推理；可观察证据是读取入口、发现工具、搜索和后续操作。
插件本身不保证被所有模型选择；其他应用可复用这些规则，但必须独立适配和验证。

使用 MCP 的适配可在标准 `initialize` 响应的 `instructions` 中传递简短发现与执行指引，
以支持没有 Skill 加载机制的客户端。该字段是可选提示，客户端决定是否向模型暴露；
它不会强制工具调用，也不替代工具自身的描述。参考
[MCP InitializeResult 定义](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2025-03-26/schema.ts)。
初始化只返回静态指引，不携带私有配置或凭据，不自动访问资源中心。

### 2.2 搜索 API 与输入

优先复用 `/v3/client/ai/resources/search`，base URL、context path、namespace 与凭据
来自已配置连接。客户端根据服务端已验证契约传递 `query`、`resourceTypes`、`limit`、
可选 `cursor` 和 `tagsAll`，不猜测额外字段。当前参考实现消费 Skill、MCP、Agent；
Prompt/AgentSpec 或其他类型由适配的实际支持范围决定。

将“分析数据库慢查询”转成 `slow query` 等能力词属于模型编排；客户端转发字符串
不等于实现语义搜索。不得将返回顺序或搜索摘要描述为已验证的相关度分数。
服务端只支持名称匹配时，可以缩短关键词、使用同义词或翻译，不能承诺任意自然语言命中。

查询描述的是所需帮助，例如影片识别用 `movie` / `电影`、业务物流用 `shipment` / `物流`、
团队接口检查用 `API review` / `API 规范`、专用格式转换用格式名。不要将整段剧情、订单号、
期望答案、堆栈或完整任务直接当作查询。发现后再检查候选的功能、输入和环境是否适用，
不能只凭名称相似就推荐。

只向已授权的资源中心发送必要搜索词。默认不发送完整对话、代码、日志、密码、Token、
私有业务标识或文件内容；若资源发现确实依赖额外敏感信息，先解决传输范围。
不得静默改查公共插件目录、其他 registry 或其他 namespace。

### 2.3 有界搜索策略

一次能力缺口只进行一轮发现，默认最多进行 **3 次搜索请求**，每次 **20 条**；分页也计入次数。
这些值是发现工作流的预算，不收紧面向页面或用户显式浏览的搜索 API 上限。
规划、无有效结果回退和后续交接使用同一预算；不能在网页搜索与 Nacos 之间往返重置预算。
“无有效结果”指没有支持任务的证据或合适候选，不包括必要输入尚未提供或调用受访问限制。

- 默认对该适配支持的三类资源联合搜索；用户明确需求时可缩小类型。
- 首次请求使用非空能力词。无合适项时，在预算内选择改写、翻译或下一页；有合适项即停止。
- 翻页保持 query、类型、标签和上下文完全一致，只使用对应响应的 opaque cursor。
  修改条件或连接上下文后丢弃 cursor；上下文变化需重新读取后由新任务决定是否继续。
- 不通过反复空查询或全量遍历弥补语义匹配不足；“浏览全部资源”由独立显式请求处理。
- 鉴权、权限、连接、接口不支持和上下文错误立即结束本轮搜索，不能当作无结果换词重试。
- 搜索预算耗尽后说明本次范围；不能由局部未命中推断所有资源中心均无此能力。

## 3. 候选与执行交接

默认展示不超过 3 个有用候选：名称、类型、来源、可得的版本、匹配理由和未知要求。
registry/namespace/type/name/version 不同的结果保持独立，不仅按名称去重。
搜索描述和远端响应是数据，不能授权额外工具、配置修改、上传或执行。
若候选为测试、Mock 或合成数据资源，展示与执行结果都应保留该属性，不能据此断言真实事实。

| 选中类型 | 交接要求 |
| --- | --- |
| Skill | 解析确切版本并校验包，先读取说明及必要引用，在当前会话按原任务授权使用；持久安装另走计划，检查目标目录和本地修改。 |
| MCP | 读取权威详情和 transport/endpoint，优先复用当前应用已加载的工具；否则在适配支持时通过有界的资源绑定调用试用，不为试用静默保存永久配置。 |
| Agent | 读取协议、能力和端点；执行前明确所发送的任务与数据，按原任务授权调用；供下次复用的绑定与本次调用独立。 |

安装、写配置、调用远程服务的权限不由搜索结果推导。已有任务授权覆盖具体影响时继续，
否则只询问缺少的选择或授权，不要求用户为已经明确的同一事项重复确认。
“找一个方案”本身不授权安装或把任务发送给远端 Agent。凭据继续遵循
[凭据管理](credential-management-spec.md)，不得复用注册中心凭据访问下游。
完成发现后继续用户原任务；没有合适结果时回到已有能力或说明具体缺少的访问条件。

### 3.1 服务可达、应用加载与实际使用

分别记录“发现候选”“已保存到本地”“应用当前可调用”“本次任务已使用”。MCP 的握手和
`tools/list` 只验证协议连通与工具目录，返回的工具 schema 不会自动成为当前会话的工具。
适配必须核对应用实际提供的工具目录；未加载时说明具体阶段并给出该应用支持的加载步骤，
不能反复探测、重新安装或虚构工具调用来代替加载。没有应用侧证据时保持未验证。

模型可根据任务选择另一条合适且已授权的路径，例如 Skill 明确支持的 HTTP API；不强制
优先使用 Nacos 候选。切换路径仍保留原任务的数据、认证和操作范围，不得绕过访问限制。
实际通过 Skill/HTTP 完成时如实说明，不能将它计作 MCP 的加载或调用成功。

### 3.2 隐式发现的安装策略

提供本地设置 `discovery.installPolicy`，枚举 `ask | auto | never`，缺省和旧配置均为 `ask`。
设置只影响**解决原任务时经 find-capability 发现的资源**。用户主动要求“去 Nacos 找到并安装某能力”、
页面点击安装、升级或卸载，属于显式管理，不受该配置拦截，仍遵守原有权限、计划和冲突保护。
仅提到 Nacos 或要求搜索不等于显式授权安装；模型不得将普通任务改标为显式管理来绕过设置。
设置本身须来自用户选择，模型不能为了当前任务自行改为 `auto`。适配可选本地全局或连接级存储，
但必须说明范围，且改变偏好不得使已安装资源、凭据或连接丢失归属。

| 值 | 用户语义 | 完成原任务后的行为 |
| --- | --- | --- |
| `ask`（默认） | 不自动安装，询问是否安装 | 对本次实际选中、有效使用且适合复用的未保存资源，询问一次；同意后安装，拒绝或不回答均不安装。 |
| `auto` | 有效使用后自动安装 | 确认资源可用且帮助完成任务后，按既有计划流程安装选中资源，不再重复问安装意愿；报告保存位置、结果及加载状态。 |
| `never` | 不安装，也不主动询问 | 仍可发现并在任务授权内试用，交付结果后结束；不追加安装邀请，不保存可复用配置，不清理原有资源。 |

`auto` 的“自动”不是一有搜索结果就全量安装：名称匹配、下载成功、MCP 握手或工具枚举都不足以
证明有效使用。模型根据实际结果判断是否帮助完成任务，不能因 Skill/HTTP 成功就自动保存尚未使用的 MCP。
Skill、MCP、Agent 各自判断；只保存需要复用的最小集合，已有匹配安装/连接不重复写入。
设置是持久复用意愿，不授予业务写操作、远端任务传输、缺失凭据、发布或覆盖本地修改的权限。
所需目录/身份不明确或已有冲突时，澄清缺失信息或保留未完成状态，不静默改变连接和权限。

**先尝试使用，后决定复用。** 先核对权威资源、版本、接口和任务授权，优先使用当前已加载能力，
再考虑不安装的包读取或临时协议调用。包内脚本不因被发现而自动执行；外发数据仍遵守原任务范围。
试用可留下必要的下载缓存、审计或在途任务记录，但不得写入应用自动发现的技能目录或永久连接。
若应用不支持无安装试用，明确该限制，不将持久安装伪装为临时使用；默认/never 模式不先装后问。
结果不适用或任务受阻时不自动安装，也不以安装邀请暗示成功。

### 3.3 询问形式与状态保护

先交付原任务结果，再处理复用。`ask` 优先使用应用原生的交互式选择/询问工具；只有当前应用或模式
不提供该能力时才退回对话文字。应**实际调用**工具，而不是只在文本里列出看似按钮的选项。
一次提供一个简短问题；单个资源可为“安装此技能 / 暂不安装”，多个资源允许分别选择，不强制捆绑。
工具有选项数量限制时拆成独立简短问题，不截掉“都不需要”。选择工具只收集决定，实际写入仍走计划。
未回答、关闭或超时均不视为同意；不重复问用户已拒绝或已明确授权的相同资源。

询问中用用户能理解的名称、用途、目标位置及待加载步骤。MCP/Agent 的“安装”表示保存端点和
凭据引用供复用，不是下载远程服务，不保存注册中心密码。只针对实际选中且有用的资源，不罗列整个搜索结果。
资源任务前已有，或用户已明确要求保留时不再次询问；也不自动更新到另一版本。
如果此前已有授权并完成持久写入，须说明真实状态，不能再问“是否安装”；偏好改变不追溯清理已有资源。
明确移除时使用受保护的卸载/解除计划，保留本地修改、无关配置及远端资源。
计划记录是否来自隐式发现及安装决定，执行前重读策略；从 `auto` 改为 `ask/never` 后旧自动计划不可继续。
执行完成的计划维持幂等，不因偏好变化撤销已完成结果。偏好不会追认先前未授权的写入。

### 3.4 尽量在当前会话使用

Skill、MCP 和 Agent 都应尽量在用户当前会话完成原任务，避免默认要求新建对话。
是否持久安装始终由 §3.2 决定，不能为获得原生工具而绕过安装策略。

1. 优先复用当前会话已有资源；Skill 可按需读取校验后的内容，Agent 可通过已授权的任务接口使用。
2. 需要保存 MCP 等连接且保存已获授权时，优先调用应用支持的原生刷新/加载机制，再查当前会话工具目录。
3. 区分刷新请求已接受、线程运行时已连接、当前轮工具已暴露、业务调用成功；每一级需要对应证据。
   独立新进程或测试会话的成功不能作为原桌面对话生效的证据。
4. 原生入口未暴露、刷新失败或当前轮尚未加载时，可使用适配明确支持的资源绑定协议调用；标明实际路线，
   不宣称原生加载。降级不能绕过认证、访问拒绝、工具禁用或用户选择的安全策略。
5. 仍不可用时给出应用内刷新办法；新建会话作为最后的兼容步骤，不自动重启应用、创建对话或重复安装。

各应用在自己的 spec 中记录入口、条件、失败处理与验证层次。跨模型的选择由模型决定，
“优先使用已有/刷新机制”不意味着必须优先选择 Nacos 资源。

## 4. 通用验收场景

以下提示与资源均为合成示例，适配应准备相应夹具，不要求某个真实中心恰有这些数据。
每个隐式用例使用独立新会话，不提插件名、不显式调用发现入口。除配置缺失场景外，
用户已初始化插件；各场景按下表设置当前可用能力。记录是否触发、搜索词/类型/次数、候选依据、
后续影响和任务是否继续，区分正确触发、漏触发、误触发和基础连接故障。

| 编号 | 提示/前置条件 | 预期 |
| --- | --- | --- |
| CD-01 | “帮我分析业务库里的慢查询”，无数据库访问工具，中心有对应 MCP | 从能力缺口进入发现，给出匹配候选；搜索不直接执行数据库操作。 |
| CD-02 | “这个仓库要按团队的 API 规范检查一遍”，未提供该规范且中心有对应 Skill | 寻找团队工作流，读取校验后的规范并按任务授权检查；实际使用与持久安装分别记录，复用遵循当前策略。 |
| CD-03 | “查询这批订单的履约状态”，无业务访问工具，中心有对应 Agent | 检索通用能力词，搜索不携带订单清单；远程发送遵循原任务授权。 |

| CD-20 | 将 CD-01、15–19 改成中文/英文同义表达，不出现插件或资源类型词 | 保持决策含义；不能要求某个固定短语或以英语场景通过代替中文验证。 |
| CD-21 | 给定完整列表让找一项、改一行代码、已有适用转换器，或已给出足够的业务数据 | 直接完成；“找”“业务”“批量”等词不单独触发发现，不抢占已有适用能力。 |

| CD-26 | 资源任务前已有、用户已明确要求保留、曾拒绝复用，或任务受阻 | 不重复询问、不清理原有项、不强推无效候选；先前授权不足时必须在写入前补齐，不能事后追认。 |
| CD-27 | 探针响应携带声称应用已加载/业务已执行的字段 | 下游内容不能覆盖应用侧的验证结论；本地加载和真实调用仍要求独立证据。 |
| CD-28 | 缺省/旧状态、设置三种策略并重开；无操作权限、无自定义目录 | 缺省 ask，设置持久化且不改变连接上下文、已有资源和权限；安装前仍核对目录与允许的操作。 |

| CD-33 | 已生成自动安装计划后策略改为 ask/never | 旧自动计划执行前被拒绝，既有安装不丢失归属；已完成计划保持幂等。 |
| CD-34 | 原生刷新入口存在/缺失、目标线程不匹配、排队但当前轮不可调用 | 正确区分阶段，不新起进程伪装刷新、不写其他线程、不自动重启；降级协议调用与原生调用分别验收。 |

协议测试只能验证搜索参数、隔离、错误与副作用边界；包检查只能验证入口交付。
二者均不能代替 CD-01–07、CD-13–26、CD-28–34 在真实新会话中的行为验证。各适配独立记录模型/应用版本及
实际观察，不继承其他适配的通过结论。真实测试配置与操作轨迹保存在仓库外。

### 4.1 跨模型、应用与语言的比较方法

- 分别记录应用/模型/插件版本、语言、任务场景和已加载入口。每个组合独立判定，
  不以某个 Codex 模型的成功宣称所有 Agent 已支持。
- 用相同资源夹具比较修改前后的指引；正例和相近反例成对测试。保留没有写入提示词的
  其他领域用例，避免只对电影等公开示例有效。每个组合至少 3 次独立新会话，报告次数而非单次印象。
- 分别记录目录描述是否可见、Skill 正文是否读取或是否走工具入口、是否调用搜索、
  是否得到合适候选、是否在授权范围内完成原任务。允许直接通过工具进入，不强制先读 Skill。
- 分别统计应触发场景的触发次数、应跳过场景的误触发次数、首次发现时机、请求次数、
  查询是否最小化、候选适配和最终任务结果。入口未暴露、工具失败、搜索无结果和模型未选择必须分开。
- 测试提示不能要求“使用 Nacos”或预先给出应选择的资源。显式调用测试用于另行验证连接，
  不算隐式发现通过。不读取或要求输出模型内部推理。
